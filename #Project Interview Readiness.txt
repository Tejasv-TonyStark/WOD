#Project Interview Readiness

Q1)Before explaining the architecture, tell me: what exact problem does your Adaptive AI Orchestration System solve? Why can't we simply send every query to the strongest LLM?

Ans)
My project is an adaptive multi-model LLM gateway that automatically selects an appropriate language model based on the incoming query. The main problem I wanted to solve is that using the strongest model for every request is inefficient because simple questions don't require the same reasoning capability as complex questions. My system therefore considers query complexity along with historical quality, latency, and cost metrics while selecting a model, with the objective of maintaining acceptable response quality while reducing unnecessary latency and inference cost. For organization-specific queries, the system activates a RAG pipeline, retrieves relevant chunks from indexed company documents using Titan embeddings and FAISS, and provides that context to the selected LLM. So the overall goal is not simply to choose the cheapest model, but to choose the model that gives the best quality–latency–cost trade-off for that particular query.


Q2)Okay, but how does your system know whether a query is simple or complex? Are you using an ML model to classify complexity?

The current system does not use an ML model for complexity classification. I implemented a heuristic complexity analyzer that considers features such as query length, reasoning-related keywords, domain-specific complexity indicators, multi-part questions, and simple-question patterns. Based on those signals, it classifies the query into low, medium, or high complexity. I chose heuristics for the prototype because the decisions are interpretable, deterministic, inexpensive, and easy to tune. A learned classifier could replace this later if we had a sufficiently labeled dataset and could demonstrate better classification accuracy

Q3)Why did you separate intent detection and complexity detection? Why couldn't you have one classifier that directly decides which model to use?

I separated intent and complexity because they represent different properties of the query. Intent helps determine whether company-specific knowledge and therefore RAG may be needed, while complexity helps determine how much reasoning capability the request requires. Keeping them separate makes the architecture modular and interpretable, and each component can be tested, tuned, or replaced independently. If I directly used one classifier to choose the final model, retrieval decisions and model-selection decisions would become tightly coupled and harder to understand or modify.



Q4)You said intent detection helps activate RAG. So how exactly does your intent detector work? Is that also purely heuristic, or do you use any semantic model there?

“Intent detection uses a hybrid approach. I first apply deterministic rules such as general-question phrases, organization-specific markers like ‘our’ or ‘this company,’ and HR-related terms such as leave, salary, resignation, or policy. When the rule-based result is ambiguous, I use a sentence-transformer semantic similarity mechanism as a tiebreaker. I didn't rely only on keywords because users can express the same intent using different wording, so semantic similarity improves coverage. However, this should not be confused with document retrieval: actual RAG retrieval uses Titan embeddings and FAISS to compare the query against indexed PDF chunks.


Q5)Why are you using sentence-transformers for intent classification, but Amazon Titan embeddings for RAG? Why not use the same embedding model for both?

The two embedding models serve different scopes. For intent detection, I only need lightweight semantic comparison between the query and a small set of predefined intent anchors, so a local sentence-transformer is sufficient and avoids an external Bedrock call. For RAG, I use Titan embeddings because the document chunks and user queries need to be embedded consistently for FAISS retrieval, and Titan was already part of the AWS Bedrock-based pipeline. Technically, I could use one embedding model for both; using two is not a strict requirement.


Q6)What exactly is an intent anchor? Where are those anchors stored, and what do you compare against them?

The intent detector first uses deterministic rules such as organization markers and HR-related terms. If those rules don't give a sufficiently clear result, sentence-transformer similarity is used as a semantic tiebreaker. Conceptually, the query representation is compared against representative intent examples or class representations to determine whether it is closer to general or organization-specific intent.”


Q7)How would the rule layer know it has a decisive result versus needing the semantic tiebreaker?

Ans)Intent detection first applies deterministic rules such as general-question phrases, organization-specific markers, and HR-related keywords. If those rules don't give a clear classification, sentence-transformer semantic similarity acts as a tiebreaker. The query is embedded and compared against representative intent examples, producing similarity scores that help determine whether the query is closer to general or company-specific intent. So I don't maintain a separate ambiguity score; ambiguity simply means the deterministic stage did not settle the classification.

My intent detector uses a hybrid hierarchical approach. First, it checks deterministic rules such as ALWAYS_GENERAL phrases, ALWAYS_SPECIFIC phrases, organization markers, and HR-related topics. If one of these rules clearly decides the intent, the system immediately returns either general or specific with a heuristic confidence value.
If the deterministic rules do not return a clear decision, the system uses a Sentence Transformer model, specifically all-MiniLM-L6-v2, as a semantic tiebreaker. The query is converted into an embedding and compared using cosine similarity against two predefined semantic anchors:
General: "What does this term mean in general?"
Specific: "What does our company policy say about this?"
If the specific similarity is greater than the general similarity and exceeds 0.35, the query is classified as specific. If the general similarity is greater and exceeds 0.25, it is classified as general. Otherwise, the result is unknown.


Q8)What are semantic anchors in your intent detector, and how can one anchor represent an entire class?

In my implementation, semantic anchors are representative sentences for each intent class. The general anchor is ‘What does this term mean in general?’ and the specific anchor is ‘What does our company policy say about this?’. I embed the incoming query and compare it with both anchor embeddings using cosine similarity. The closer anchor helps resolve intent when deterministic rules don't decide it. However, one sentence cannot perfectly represent an entire semantic class, so this is a prototype limitation. A stronger implementation would use multiple representative examples per class or compute class-centroid embeddings and validate the thresholds on labeled queries.


Q9)Orchestartor working?
The orchestrator combines intent, complexity and retrieval requirements into an execution strategy such as fast, reasoning, fast+RAG or reasoning+RAG. It does not directly select the model.
