Q1)What is an Atomic Instruction?
An atomic instruction is a hardware-supported instruction that executes as one indivisible operation, ensuring no other thread or processor can interrupt or observe it midway. This property is essential for implementing synchronization mechanisms such as Test-and-Set and Compare-and-Swap.






Suppose two threads want to update the same bank balance.

We already have Test-and-Set and CAS.

So why do you think we still need something called a Mutex?

A mutex is needed because directly using atomic instructions such as Test-and-Set can cause busy waiting. If one thread owns the lock, other threads may repeatedly check it and waste CPU cycles. A mutex provides a higher-level locking mechanism where a waiting thread can be blocked and placed in a waiting queue. When the owner releases the mutex, the OS wakes one of the waiting threads. A mutex also provides ownership, meaning only the thread that acquired it should release it.





Q2)
Thread A executes:

and enters the critical section.

Thread B then executes:

No. Thread B cannot unlock the mutex because it does not own it. A mutex enforces ownership: only the thread that successfully acquired (locked) the mutex is allowed to release (unlock) it. Allowing another thread to unlock it could cause inconsistent behavior and violate synchronization correctness.


Q3)Suppose Thread A does:

mutex.lock();

/* Critical Section */

While Thread A is inside the critical section, Thread B calls:

mutex.lock();
Question:

What exactly happens to Thread B?

When Thread B tries to acquire a mutex that is already locked by Thread A, it does not busy wait. Instead, the operating system blocks Thread B and moves it to the waiting (blocked) queue. The CPU is then free to execute other runnable threads. Once Thread A releases the mutex, the OS wakes one of the waiting threads, allowing it to acquire the mutex and continue execution. This avoids wasting CPU cycles, unlike a pure Test-and-Set implementation.


Q4)What is a Mutex?

A Mutex (Mutual Exclusion) is a synchronization primitive that ensures only one thread can access a critical section at a time. It provides ownership, meaning only the thread that acquires (locks) the mutex can release (unlock) it. If another thread attempts to acquire a locked mutex, it is blocked by the operating system and placed in a waiting queue until the mutex becomes available.


Q5)What is a spin Lock?

A Spinlock is a synchronization mechanism in which a thread repeatedly checks (spins on) a lock until it becomes available instead of being blocked by the operating system. It uses busy waiting to achieve mutual exclusion and is typically implemented using atomic instructions such as Test-and-Set or Compare-and-Swap (CAS).


Q6)
Suppose the critical section executes for only 5 CPU instructions.

Would you prefer:

Spinlock
Mutex

Why?

I would prefer a Spinlock because the critical section is very short (only about 5 CPU instructions). Blocking a thread using a Mutex involves a context switch, moving the thread to the waiting queue, and later waking it up. This overhead may take longer than simply spinning for a few CPU cycles. Therefore, for very short waiting times, a Spinlock is more efficient.


Q7)If Thread B is continuously spinning on the only CPU, when will Thread A get CPU time to finish the critical section and release the lock?

A Spinlock is generally not suitable on a single-core processor because the waiting thread continuously spins while occupying the only CPU core. As a result, the thread holding the lock may not get CPU time to complete its critical section and release the lock. This wastes CPU cycles. In such cases, a Mutex is preferred because the waiting thread is blocked, allowing the lock-owning thread to continue execution and release the mutex.


Note:
Spinlock → Best for multicore systems with very short critical sections.
Mutex → Best for long waits or single-core systems, because blocked threads don't waste CPU time.
If the critical section is very short and the system has multiple CPU cores, a Spinlock is the better choice because the waiting time is small and avoiding a context switch is more efficient. However, if the waiting time is long, there are many competing threads, or the system has a single CPU core, a Mutex is preferred because it blocks waiting threads instead of wasting CPU cycles by spinning.


Q8)Why do we need semaphore?
A Mutex allows only one thread to access a resource at a time. However, if multiple identical resources are available (for example, 5 printers or 10 database connections), allowing only one thread would underutilize the available resources. This increases waiting time and reduces throughput. Therefore, we need a synchronization mechanism that allows a fixed number of threads to access the resources simultaneously. This mechanism is called a Semaphore.


wait(P)

Decreases the semaphore value by 1. If no resources are available, the calling thread is blocked and placed in the waiting queue.

signal(V)

Increases the semaphore value by 1. If threads are waiting, the OS wakes one waiting thread and allows it to proceed.

Operating Systems – Classical Synchronization Problems (Interview Summary)

These are the three most important classical synchronization problems asked in interviews. They demonstrate how synchronization primitives such as mutexes and semaphores are applied to solve real-world concurrency issues.

Q1) What are Classical Synchronization Problems?

Classical Synchronization Problems are standard Operating System problems used to demonstrate how multiple threads or processes safely access shared resources while preventing race conditions, deadlocks, and starvation. They are commonly solved using synchronization mechanisms such as Mutexes and Semaphores.

The three classical synchronization problems are:

Producer–Consumer Problem
Readers–Writers Problem
Dining Philosophers Problem
1. Producer–Consumer Problem
Definition

The Producer–Consumer Problem involves one or more producer threads that generate data and place it into a shared buffer, and one or more consumer threads that remove data from the same buffer. The objective is to synchronize access to the buffer while preventing overflow, underflow, and race conditions.

Problem Statement

A bounded buffer of size N is shared between producers and consumers.

Problems:

Producer should not produce when the buffer is full.
Consumer should not consume when the buffer is empty.
Producer and Consumer must not modify the buffer simultaneously.
Synchronization Variables
mutex = 1
empty = N
full = 0
mutex

Ensures that only one producer or consumer accesses the shared buffer at a time.

empty

Represents the number of empty slots available in the buffer.

full

Represents the number of filled slots (items) available for consumption.

Producer Algorithm
wait(empty);
wait(mutex);

/* Produce Item */

signal(mutex);
signal(full);
Consumer Algorithm
wait(full);
wait(mutex);

/* Consume Item */

signal(mutex);
signal(empty);
Why this Order?

Producer:

wait(empty);
wait(mutex);

First check whether space exists.

Only then acquire the mutex.

Otherwise, the producer may hold the mutex while waiting, preventing the consumer from removing items and causing deadlock.

Similarly,

Consumer:

wait(full);
wait(mutex);

First verify that an item exists.

Only then enter the critical section.

Interview Questions
What does empty represent?

Number of free slots available for production.

What does full represent?

Number of items available for consumption.

What does mutex represent?

Ensures mutual exclusion while accessing the shared buffer.

Advantages
Prevents race conditions.
Prevents buffer overflow and underflow.
Efficient synchronization between producers and consumers.
Limitations
Incorrect ordering of semaphore operations can lead to deadlock.
Busy waiting occurs if implemented using spinlocks.
2. Readers–Writers Problem
Definition

The Readers–Writers Problem synchronizes access to shared data where multiple readers may read simultaneously, but writers require exclusive access.

Problem Statement

Many readers and writers share the same file/database.

Rules:

Multiple readers may read simultaneously.
Only one writer may write.
Readers and writers cannot access the data simultaneously.
Why?

Reading does not modify data.

Writing modifies shared data.

Allowing a writer and reader together can produce inconsistent or partially updated information.

Rules
Reader + Reader

✅ Allowed

Writer + Writer

❌ Not Allowed

Reader + Writer

❌ Not Allowed

Major Problem
Writer Starvation

If readers continuously arrive, the writer may never obtain access to the shared resource.

Advantages
Maximizes concurrency for read-heavy workloads.
Improves system throughput.
Widely used in databases and file systems.
Disadvantages
Writer starvation may occur.
Fair scheduling is required to avoid indefinite waiting.
Applications
Databases
Shared files
Caches
Configuration files
Operating System kernels
3. Dining Philosophers Problem
Definition

The Dining Philosophers Problem models multiple processes competing for a limited number of shared resources and demonstrates how improper resource allocation can lead to deadlock.

Problem Statement

Five philosophers sit around a circular table.

Between every two philosophers is one fork.

Each philosopher requires two forks to eat.

What Happens?

Suppose every philosopher picks up the left fork simultaneously.

Each philosopher now:

Holds one fork.
Waits for the other fork.

No philosopher can proceed.

No philosopher releases the held fork.

Result
Deadlock

Every philosopher waits forever.

Why is it Important?

It demonstrates:

Deadlock
Resource allocation
Circular wait
Mutual exclusion

These concepts directly apply to Operating Systems.

Solution Approaches
Limit the number of philosophers allowed to eat simultaneously.
Pick forks in a predefined order.
Use an arbitrator (waiter).
Use resource hierarchy.
Applications
Resource allocation
Database locking
Network resource management
Multithreading
Operating System scheduling

Interview One-Liners
Producer–Consumer

Synchronizes producers and consumers sharing a bounded buffer while preventing overflow, underflow, and race conditions.

Readers–Writers

Allows multiple readers to access shared data simultaneously while ensuring writers have exclusive access to maintain consistency.

Dining Philosophers

Demonstrates how improper allocation of shared resources can lead to deadlock and is used to study synchronization and resource allocation.

Key Interview Takeaways
Producer–Consumer → Focuses on buffer management using empty, full, and mutex.
Readers–Writers → Focuses on data consistency, allowing concurrent reads but exclusive writes. Main issue: Writer Starvation.
Dining Philosophers → Focuses on resource allocation and demonstrates Deadlock through circular waiting.
